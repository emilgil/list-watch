## What it is

Amazon List Watch ("listwatch") scrapes shared/public wishlists on amazon.se, stores per-product price history, and sends Apprise notifications when a price drops below a configured level. It is self-hosted in a Debian 13 LXC (Proxmox), single user, no login (LAN/Tailscale only), with its own web UI.

## Planned architecture (from the spec)

- **One Python 3.13 process** runs scheduler, collector, alert engine and web UI over one SQLite DB (WAL mode). Don't split into services.
- Stack: FastAPI + Jinja2 + HTMX (no frontend build), Chart.js, httpx + selectolax, APScheduler (interval with jitter), Apprise as a library (no Apprise server).
- **Collector sits behind a common source interface** so other sources (e.g. Hagglezon) can be added later without touching alerts or the GUI. The **parser is an isolated module** whose tests use saved real Amazon HTML pages as fixtures.
- Collection strategy (revised after the 2026-10-25 probe, see `spec-probe-findings.md`): the wishlist page (paginated) is the **only** price source each round; no product page is fetched for price. Local ASIN watches always use the product page.
- **The list page never shows Prime status**, only the product page `amazon.se/dp/<ASIN>` does. Prime is cached per ASIN (`prime`/`inte_prime`/`okänd` + checked-at). A product page is fetched only (a) when a price meets an alert condition and Prime is unknown or older than `prime_fresh_for_alert`, in which case the alert waits for the check and fires only if `prime`; or (b) as background refresh when the cache is older than `prime_ttl`, max `max_product_pages_per_round`, `saknar_pris` products first (only the product page can tell they're out of stock), then oldest first. On CAPTCHA/HTTP error on a product page: stop product-page fetches for the rest of the round, leave status unchanged, send no alert that needed the check.
- Logged out, the product page shows no Prime badge either (all `isPrimeEligible` flags are false). Rule: Prime badge **or Amazon as shipper** in the buy box ⇒ `prime` (the shipper row is labelled "Avsändare", "Avsändare / Säljare" or, when Amazon ships for a third-party seller, "Skickas från" next to "Säljs av"; seen on the first real collect 2026-10-25); other shipper ⇒ `inte_prime`; neither visible ⇒ `okänd`. Agreed 2026-10-25 as a first approximation.
- Each list item gets a status: `pris`, `ej_i_lager` (explicit unavailable marker) or `saknar_pris` (neither price nor marker). The real list page has **no** out-of-stock marker; unpriced items just say "Visa alla köpalternativ", so the product page decides at the next background refresh.
- Collector details beyond the spec: Prime background refresh runs right after each list is read, for that list's products, logged in that list's run, with the `max_product_pages_per_round` budget shared across the omgång. A list `saknar_pris` never overrides an `ej_i_lager` set by a product page. `product.senaste_pris_ore` keeps the last known price through `ej_i_lager`/`saknar_pris`, so a return to the same price is no change. A failed list read (CAPTCHA/HTTP/0 items) never marks items as removed. Ops notifications per list (migration 0003: `wishlist.fel_i_rad`, `wishlist.parserfel`): unreadable 2 omgångar in a row, not counting blocks (0 items or HTTP 403/404/410 ⇒ status `privat`, shown as "Ej åtkomlig"; a private, removed and emptied list all look the same: HTTP 200 with no items, checked 2026-10-25), plus a notice when it reads again; parse errors when > 20 % and ≥ 3 of a list's items aren't understood (no ASIN, no title, or price lost this omgång), notified once until back under. All ops notices go through `collector.send_ops_notice` (drift_notis event). All HTTP goes through `fetcher.polite()`.
- The list page contains hidden error templates ("Ett fel inträffade…", "Amazon har stött på ett fel") inside `aok-hidden`/`a-hidden` elements next to every item. Ignore them; they are not product errors or blocking.
- Politeness is a requirement: one request per 5–15 s (random), realistic User-Agent, `Accept-Language: sv-SE`; on CAPTCHA/HTTP 503 back off exponentially; after 3 blocked rounds in a row send an ops notification.
- Parse prices to **integer öre**; never store floats. Formats seen: Swedish "1 299,00 kr" (space/NBSP/narrow NBSP thousands), "kr217,90", and English "kr1,299.00"/"kr115.66" depending on locale. A row can repeat the price ("217,90 kr kr217,90"): take one price, never sum.

### Data model
Schema lives in `src/listwatch/migrations/NNNN_*.sql`, applied by `listwatch migrate` via `PRAGMA user_version` (backup first). SQL column names are ASCII (`pris_öre` → `pris_ore`). Core tables: `wishlist`, `product` (ASIN PK), `wishlist_product`, `price_point`, `alert_rule`, `settings` (Apprise URLs, intervals live in DB, not env). Run log (`docs/spec-logg.md`): `run` (one per list per execution, grouped by `omgang`, counters stored on the row) and `event` (only on change, e.g. `saknar_pris` is logged when the status changes, not every round). There is no `notification_log`: alert/ops/test notifications are `event` rows, kept `notislogg_lagringstid_dagar` (365); other events and runs are purged after `logg_lagringstid_dagar` (30). Probe runs write `run`/`event` only, never product or price data. If a product is in several lists, only the first list's run writes its `price_point` and events. A product in several lists is stored and measured once. `product` also holds the Prime cache (`prime_status`, `prime_kontrollerad`). `price_point` has `status` (`pris`/`ej_i_lager`/`saknar_pris`); `pris_öre` is NULL unless status is `pris` (still recorded; graphs show a gap), and `prime` is the cached status at measurement time (ja/nej/okänd). Settings `prime_ttl` (7 d), `prime_fresh_for_alert` (24 h), `max_product_pages_per_round` (10). Removed list items are marked inactive, history is kept.

### Alert rules (easy to get subtly wrong — read the spec's "Larmlogik")
- Reference price = **median of valid Prime measurements over the last 90 days** (use less history if that's all there is; no percent alert before 7 days of data).
- Triggers: fixed price (`price ≤ target`) and/or percent (`price ≤ ref × (1 − pct/100)`); any active condition fires. Per-product rule overrides list default; if inheriting, use the **lowest** percent among the lists containing the product.
- Alert fires on downward crossing, then is suppressed until price drops a further ≥5 % below `senaste_larm_pris` or goes back above the level (which resets it).
- Only **Prime** offers alert. Prices <10 % of the median are "suspicious" and don't alert until confirmed by the next measurement.
- Optional "all-time low" alert, only after ≥30 days of history.
- Decided details (spec Larmlogik 5–9): the reference excludes the point being judged; non-`pris` points neither alert nor reset; a suspicious price is confirmed by a next price within ±10 % (in `collector._suspicious`); `senaste_larm_pris` is set only after a successful send; the Prime check result is written back into the current `price_point.prime`. Apprise URLs are the `apprise_urls` setting, one per line.

## Build order

**Step 0 is `listwatch probe <url>`**, built before the rest: fetches a list with the service's real HTTP settings and reports HTTP status, CAPTCHA detection, page/product counts, and share of products with readable price / Prime status; saves raw HTML under `/var/lib/listwatch/probe/<date>/` (these become parser fixtures). Exit codes: 0 every item has a price or an out-of-stock marker, 1 some `saknar_pris`, 2 blocked/error. Missing Prime on the list page is expected and does not affect the exit code (the report says "finns ej på listsidan (förväntat)"). Output includes a terminal report (price read, Prime, out of stock, missing price, and "product pages needed per round" = missing-price count), saved `page-N.html` files and a `report.json` (same numbers plus one row per product: ASIN, title, status, price, Prime). The first real probe (list "Hemmet", 55 items, 44 priced) is in `/home/dev/probe-out/2026-10-25_1541/`; trimmed excerpts of it are the `tests/fixtures/real_*` files.
